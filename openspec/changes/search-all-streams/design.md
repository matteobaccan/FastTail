## Context

Each `TailEngine` owns at most one `ScanJob` (`job: Option<ScanJob>`) and uses it for its index, filter, search, level and (with `background-timestamp-scan`) timestamp scans; a newer request cancels the running one. A `Search` job streams the file from its own `FileSource`, evaluates the stream's `FilterSpec` (include, exclude, minimum level, stack-trace continuation rule) and the lower-cased query, and sends ordered batches of line indices tagged with a generation. The UI is an `egui_dock` `TabViewer` over `FastTailTab` (`LogStream(path)`, `Filters`, `Highlights`, `Settings`); switching tabs is done by the app through `dock_state.find_tab` + `set_active_tab`, and `focused_stream` routes the stream shortcuts. The `search-results-pane` change introduces `src/ui/hit_list.rs` and a Search job that keeps counting past its storage limit.

## Goals / Non-Goals

**Goals:** one query over every open stream without disturbing their own searches and filters; responsive with ten multi-GB streams; bounded CPU, threads and memory; a result always lands on the right line or says it cannot.

**Non-Goals:** searching files that are not open, or closed tabs; regex or case-sensitive search (the per-stream search has neither); live-updating results as streams grow; a merged, time-ordered result list (that is the `merged-timeline-view` change); replacing text.

## Decisions

- **Jobs owned by the session, not by the engines.** `FindAllSession` spawns its own `ScanJob` per stream with `ScanJob::spawn(path, range, JobSpec::Search { .. })`. The engine's single job slot is left alone, so a find-all never cancels, and is never cancelled by, the stream's own filter, search, level or timestamp scan. The range is `[BOM length, file length at start)` of the stream's current file (the resolved file of a pattern stream), with the stream's `FilterSpec` cloned at start. *Alternative:* run the query through each engine's job slot. Rejected: it would cancel the user's own per-stream search and filter scans and serialise behind them.

- **Bounded concurrency.** At most `min(4, std::thread::available_parallelism())` jobs run at once; the others wait in a FIFO in the order of the dock tabs. When a job finishes, fails or is cancelled, the next one starts on the next poll. A stream whose line index is still being built waits in the queue until it is ready, so result line numbers always exist in its index. Each job reads through its own file handle and 1 MB buffer, so peak extra memory is a few MB plus the stored hits. *Alternative:* one thread per stream. Rejected: twenty open streams would mean twenty concurrent sequential readers on one disk.

- **Same match semantics as the per-stream search.** Case-insensitive substring on the decoded line, over the lines the stream shows: its include/exclude/level filter runs in the job, and its time window, if any, is applied to each drained batch with `TailEngine::in_time_range` (the same drain-time rule `background-timestamp-scan` introduces for the stream's own jobs). Streams in HEX view are skipped and listed as skipped, because their search is byte-level. The query is a snapshot: typing in the Find results box does not re-run until `Enter` or the Find button, avoiding N jobs per keystroke.

- **Caps.** At most 100,000 hits are stored per stream (800 KB); the job keeps counting past it (`count_past_limit`) so the group header shows the true total with a "first 100,000 listed" note. The per-stream search keeps its own, larger cap from `search-results-pane`; find-all uses a smaller one because it multiplies by the number of streams.

- **Cancellation.** A new query, the Stop button and closing the Find results tab drop the session's jobs (dropping a `ScanJob` sets its cancel flag; the worker checks it per chunk). Closing a stream drops its group and job. A stream that is reloaded (truncation, rewrite, rotation, pattern switch) bumps the engine's `reload_generation`; its group is marked stale, its running job is cancelled, and its rows stay visible but dimmed with a "stream changed — Refresh" note instead of jumping by an index that now means another line.

- **Tab and layout.** `FastTailTab::FindResults` is a single tab: `Ctrl+Shift+F` focuses it if present, otherwise adds it split below the first leaf of the main surface; it is closable and is not written to the saved dock layout (results are not persisted). The shortcut is consumed in the app before the dock is drawn, because egui's logical shortcut matching lets the stream's `Ctrl+F` (`consume_shortcut` with `CTRL`) also fire on `Ctrl+Shift+F`. The tab body is the query box, Find / Stop / Refresh buttons, a summary (`42 matches in 3 of 7 streams`, running count, snapshot time) and the grouped list.

- **One virtualized list, shared widget.** The groups are flattened into rows — a header row per stream, then its hits when expanded — and drawn with `show_rows` over the total row count; row `i` is resolved to (group, hit) with a prefix sum over the group sizes, recomputed once per frame (O(streams)). Rows are drawn by `src/ui/hit_list.rs` from `search-results-pane`, extended with a header-row kind: same line-number column, level colour, truncated text with query tinting, keyboard selection (`↑`/`↓`, `PgUp`/`PgDown`, `Ctrl+Home`/`Ctrl+End`), `Enter` / click commit and `Esc`. Text is read with the stream engine's `get_line` for the rows on screen only. *Alternative:* one `CollapsingHeader` with its own scroll area per stream. Rejected: nested scroll areas in egui fight over the wheel and none of them is virtualized across groups.

- **Jumping to a result.** The tab cannot change the dock while it is drawn, so a commit writes a focus request `(path, line)` into the dock context; after the dock is drawn the app finds the stream's tab, activates it, sets `focused_stream`, and on the engine sets `scroll_to_line` to the line (or, if the stream's filters changed since and now hide it, the next visible line, via the same `goto_target_for` logic as Ctrl+G), pauses follow and selects the row so it is visible. The stream's own query and matches are untouched. `F3` is not handled by the Find results tab; after a jump the stream's panel has focus, so `F3` there walks the stream's own matches as before.

## Risks / Trade-offs

- [Four concurrent scans can saturate a slow disk and make the focused stream's own scan slower] → the limit is small and fixed, and every job is cancellable with Stop.
- [Snapshot results go stale on busy streams] → the snapshot time is shown and Refresh is one click; live results would mean N jobs restarting on every append.
- [Stale detection only covers reloads; appended lines never invalidate earlier indices] → correct by construction, since appends do not move existing line indices.
- [A stream whose filter changes after the search may no longer show a result line] → the jump lands on the next visible line and the stream's go-to notice says so, as for Ctrl+G.
