## Context

Per stream, `TailEngine` holds `search_matches: Vec<usize>` (ordered line indices of the visible lines containing the query, case-insensitive), `current_match_idx`, and fills the list synchronously up to 16 MB or through a `Search` scan job above, appending batches as they arrive and extending it incrementally on append (`refresh_search_from`). The list is capped by `MAX_SEARCH_MATCHES = 20_000`, silently: the counter shows the stored count. Bookmarks are a `BTreeSet<usize>`; levels are a `Vec<u8>` prefix cache. The rows are drawn by `ScrollArea::show_rows` in `src/ui/dock.rs` (and by `wrap_layout` in wrap mode), and `focused_stream` decides which stream reacts to `F3`, `Ctrl+F`, `Ctrl+G` and the navigation keys.

## Goals / Non-Goals

**Goals:** see all hits of a search at once and jump to any of them; see where hits, bookmarks and errors sit in the file; stay flat in cost with millions of lines and hundreds of thousands of hits; one clear keyboard model.

**Non-Goals:** a regex or case-sensitive search mode (the query semantics stay as they are); a results pane for HEX byte hits; editing, exporting or bookmarking from the pane beyond what the main view offers (export of matches already exists); searching several streams (the `search-all-streams` change).

## Decisions

- **The pane lives inside the stream tab, not as a dock tab.** It is a resizable bottom region of the stream's panel (`TopBottomPanel::bottom(..).resizable(true).show_inside`), so it moves, splits and closes with its stream and needs no tab-to-stream binding. Open/closed and height are global preferences (`search_pane`, `search_pane_height` in `fasttail.ini`) applied to every stream; the pane shows only while the stream has an active query, and says "no matches" when the list is empty. *Alternative:* a separate "Search results" dock tab following the focused stream. Rejected here: it breaks when two streams are side by side; the dock-tab form is what `search-all-streams` uses, because there the results span streams.

- **Virtualized over the existing hit list.** `show_rows(row_height, search_matches.len())` reads only the lines on screen through `get_line` (block cache), so the pane costs the same with 10 or 1,000,000 hits. Each row shows the 1-based line number, the level colour when level colouring is on, and the line text truncated to the pane width with the query spans tinted; highlight rules are not re-run in the pane. New hits from a running job or from appended lines appear as the list grows; when the pane was scrolled to its last row it sticks there.

- **Shared hit-list widget.** `src/ui/hit_list.rs` takes a slice of line indices, a line source (`&TailEngine`), the query for tinting, the index of the current hit and returns the clicked / committed hit. `search-all-streams` renders one instance per stream group with the same widget, so row layout, tinting, keyboard handling and virtualization are written once.

- **One cursor, the current match.** Clicking a pane row sets `current_match_idx` to that hit, sets `scroll_to_line` to centre it in the main view and pauses follow, exactly as `F3` does. With the pane focused, `↑`/`↓`, `PgUp`/`PgDown`, `Ctrl+Home`/`Ctrl+End` move a pane selection without moving the main view; `Enter` commits the selection like a click. Whenever the current match changes (click, `Enter`, `F3`, `Shift+F3`, a search refresh), the pane selection snaps back to it and the pane scrolls to keep it visible. *Alternative:* moving the selection scrolls the main view on every arrow press (klogg's behaviour). Rejected: on a large file each press would move the view by thousands of lines and fill the block cache for rows the user is skipping.

- **Focus rules.** Clicking in the pane focuses its stream's dock panel (the pane is part of it) and gives the pane keyboard focus. While the pane has keyboard focus, the navigation keys listed above act on the pane, and `Esc` returns keyboard focus to the main view. `F3` / `Shift+F3`, `Ctrl+F`, `Ctrl+G`, `F2` / `Ctrl+F2`, `Alt+W`, `Space` and `Ctrl+C` keep their stream meaning whether the pane or the main view has focus (`Ctrl+C` with nothing selected copies the current hit, which is the pane's committed row). Streams in other panels never react. Clicking a row in the main view gives focus back to the main view.

- **Match cap: 1,000,000 stored hits per stream, true total counted.** 8 bytes per hit bounds the list at 8 MB per stream, in line with the "match lists" already allowed as resident state. Past the cap the synchronous path and the `Search` job (`count_past_limit: true`) keep scanning to count without storing; the engine keeps `search_total`. The counter reads `[current / total]` and adds `(first 1,000,000 listed)` when capped; the pane header shows the same. `F3` wraps within the stored hits. HEX byte hits keep their 20,000 cap. *Alternatives:* keep 20,000 (a pane that stops at 20,000 of 3 million matches silently is misleading), or unbounded (a search for `e` on a 20 GB log would allocate gigabytes). A search that matches more than a million lines is better narrowed with a filter, and the header says how many there are.

- **Overview strip as a cached per-pixel mark map.** A 10 px strip is allocated at the right edge of the stream's rows area, beside the scrollbar, and maps visible row `r` of `n` to `y = r / n * height`. Its cache is one byte of flags per pixel (hit, bookmark, error, current match), rebuilt only when an input changes: strip height, visible row count, search generation, bookmark set, level cache length, filter generation. While the stream grows, rebuilds are throttled to at most 4 per second.
  - *Hits and bookmarks:* exact — each hit or bookmark's visible row is found by `get_visible_row_of_line` (binary search in `filtered_lines`, identity without filters): at most 1,000,000 lookups per rebuild.
  - *Errors (ERROR and FATAL):* without an active filter, exact from per-4096-line error counts that the engine maintains in `push_levels` / `truncate_levels` (one `u32` per 4096 lines); with a filter and up to 4,000,000 visible rows, exact by walking the visible rows' cached levels; above that, sampled — each pixel inspects at most 256 evenly spaced visible rows, and the strip's tooltip says the error marks are sampled. Lines whose level is not cached yet (Levels job running) carry no mark until it is.
  - Click or drag on the strip scrolls the main view so that row is centred and pauses follow; hovering shows the line number under the pointer. The strip is hidden in HEX and rendered Markdown views, and when there is nothing to mark. A Settings checkbox turns it off (`overview_strip`, default on).

## Risks / Trade-offs

- [The pane steals vertical space from the log] → off by default, resizable, remembered; a stream without a query shows no pane.
- [Sampled error marks can miss an isolated error on a filtered view of more than 4 million rows] → disclosed in the tooltip; unfiltered views and every ordinary file are exact.
- [Counting past the cap makes a very broad search on a huge file read the whole file instead of stopping at 20,000] → it runs on the worker with progress and is cancelled by the next keystroke, as any search; the synchronous path only applies up to 16 MB.
- [Raising the cap raises worst-case memory from 160 KB to 8 MB per stream] → acceptable next to the 8 bytes per line index; documented.
- [Two keyboard targets inside one panel can confuse] → the pane draws a focus outline when it has keyboard focus, and `Esc` always returns to the main view.
