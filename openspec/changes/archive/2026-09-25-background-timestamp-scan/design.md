## Context

`TailEngine` keeps `timestamps: Vec<i64>` (one effective timestamp per indexed line, `NO_TIMESTAMP` before the first timed line), plus `timestamp_hint`, `timestamps_parsed` and `timestamps_unordered`. The cache is a prefix of the line index and is filled by `fill_timestamps` in passes of `TIMESTAMP_FILL_BUDGET` (200,000) lines; `ensure_timestamps` loops those passes to completion. Four places call it synchronously: `set_time_range`, `apply_time_range_text`, `resolve_goto` (a `:` in the Ctrl+G input) and the append path in `rebuild_line_index_from` once the cache is non-empty.

Every other whole-file pass goes through `scan_job`: one `ScanJob` per stream (`job: Option<ScanJob>`), a worker with its own `FileSource`, 1 MB chunks, batches tagged with a generation, a cancel flag checked per chunk, and `scan_progress()` feeding the `⏳ kind 37% (n)` label in the stream bar. `Levels` is the closest model: a per-line cache that is a prefix of the index, filled synchronously below `job_threshold_bytes` (16 MB of remaining bytes) and by the lowest-priority job above it, resumed by `ensure_levels()` from `levels.len()` whenever a job ends.

Two related interface-thread passes exist today: `recompute_filtered_lines_from(0)` does not start a Filter job while a time window is set ("the job filters text, and the window needs the timestamp cache that lives here"), and a Search job carries only the text/level `FilterSpec`, so the time window is not applied to its hits.

## Goals / Non-Goals

**Goals:** no whole-file timestamp pass on the interface thread; progress in the stream bar like the other scans; the time range and go-to-time apply automatically when the cache is complete; identical cache contents to the synchronous path; a preempted scan does not start over.

**Non-Goals:** timing files proactively on open (the cache stays on demand, 8 bytes per line is not free); applying a partial window progressively while the scan runs; parallel scans per stream (still one job at a time); changing the timestamp formats or the inheritance rules.

## Decisions

- **A `Timestamps` scan kind that mirrors `Levels`.** `JobSpec::Timestamps { inherited: i64, hint: FormatHint }` carries the state `fill_timestamps` reads from the prefix (the timestamp of the last timed line and the last matched format). The worker calls `crate::timestamp::detect_timestamp` per line — already pure and allocation-free, so it is `Send`-safe — and sends `ScanBatch::Timestamps { values: Vec<i64>, parsed: usize, unordered: bool, hint: FormatHint }` once per 1 MB chunk. The engine appends `values`, adds `parsed`, ORs `unordered` and stores the hint, exactly what `fill_timestamps` does at the end of a pass; `job.hits` reports `timestamps.len()`. *Alternative:* run `fill_timestamps` in 200,000-line slices once per frame on the interface thread. Rejected: it still costs a frame budget per slice, reads through the block cache and evicts the rows being viewed, and would be the only scan with its own progress plumbing.

- **One entry point, `request_timestamps()`.** It replaces the four synchronous calls. If the untimed remainder (`source.len() - line_offsets[timestamps.len()]`) is at most `job_threshold_bytes`, it times the rest synchronously as today (small files and appends stay instant and keep every existing test meaningful). Otherwise it sets `timestamps_wanted` and starts the job when the priority rules allow. `ensure_timestamps()` stays public and synchronous for the tests and the bench's "timestamp cache" phase. *Alternative:* always use the job. Rejected: a thread spawn for a few KB of appended lines, and a visible `timing lines` flicker on every append.

- **Priority between jobs.** Index first: nothing timestamp-related starts while `index_pending`. A timestamp request preempts a running `Levels` job (levels resume from their prefix afterwards through the existing `ensure_levels()` call in `finish_job`). A timestamp request during a Filter or Search job is queued in `timestamps_wanted` and started from `finish_job` before `ensure_levels()`. A filter or search request during a Timestamps job is deferred (`pending_filter` / `pending_search`, as during indexing) while a time window is set or pending, because its result depends on the cache; with no window involved (a Ctrl+G jump, or a future consumer such as the timeline histogram) it cancels the Timestamps job, which resumes from `timestamps.len()` after the filter or search ends. A reload, truncation or rewrite cancels everything, as today. *Alternative:* let any filter/search cancel the timestamp scan. Rejected: with a window set the filter would run without the cache, then run again.

- **Resumable by construction.** Batches are appended in order and the job range starts at `line_offsets[timestamps.len()]`, so cancelling at any point leaves a valid prefix and the next job continues from it with `inherited = timestamps.last()` and the stored hint. `truncate_timestamps` already handles an index that changed under the prefix; the drain drops batches of a replaced generation.

- **Pending window, applied at completion.** `apply_time_range_text` stores the two texts and, if the cache is not complete, sets `time_range_pending` without touching `time_from` / `time_to`: the view keeps its previous state instead of hiding lines that simply have not been timed. When the Timestamps job finishes, the engine re-reads the texts (the reference day comes from the first timestamp, known only now), calls `set_time_range`, clears the flag, and the filter refresh starts a Filter job as usual. Editing the fields while pending just replaces the texts; clearing them drops the pending window. *Alternative:* apply the window progressively on the timed prefix. Rejected for this release: an ordered log would work, but lines past the prefix would have to be shown or hidden arbitrarily until timed, and "Known issue" fixes should not introduce a half-filtered state.

- **Pending go-to-time.** `resolve_goto` returns a new `GotoTarget` state ("waiting for timestamps") instead of `None` when the input contains `:` and the cache is incomplete on a large stream; the engine stores the input in `pending_goto_time` and the popup shows `timing lines 37%`. At completion the input is resolved with `goto_time` and `scroll_to_line` is set, pausing follow as a normal jump does. Closing the popup (Esc) or entering another target clears the pending jump; the scan keeps running because the cache is useful.

- **Time window applied to job results at drain time.** Filter and Search jobs keep evaluating text and level only; when a batch of line indices is drained, the engine keeps only the indices for which `in_time_range(idx)` holds (an O(1) lookup in the complete cache). This removes the `!self.is_time_filtered()` exception in `recompute_filtered_lines_from`, so a window on a 20 GB file no longer filters on the interface thread, and makes large-file search hits respect the window as the synchronous path does. *Alternative:* share the cache with the worker through an `Arc<[i64]>` snapshot. Rejected: the cache grows on append and would need copy-on-write; the drain filter is simpler and exact.

- **Status and localisation.** `scan_kind_key` maps `Timestamps` to a new key `scan_timestamps` ("timing lines"); the pending hint next to the time fields uses `time_range_pending` ("applies when timing finishes"); the Ctrl+G popup reuses `scan_timestamps` with the percentage. Both keys are added to all 16 languages; the i18n coverage test enforces it.

## Risks / Trade-offs

- [The window does nothing visible for several seconds on a huge file] → the pending hint and the stream-bar progress say why; the alternative was a frozen window.
- [A filter typed during the scan waits for it when a window is set] → the filter box stays editable and the stream bar shows which scan is running; the deferred filter starts as soon as timing ends.
- [Batches of `i64` values are 8 bytes per line over the channel] → the same size as the resulting cache and one batch per 1 MB chunk; comparable to the `Offsets` batches of the index job.
- [Two paths (sync below the threshold, job above) must fill identical caches] → a test times the same file both ways and compares `timestamps`, `timestamps_parsed`, `timestamps_unordered` and the final hint, including a job preempted halfway and resumed.
